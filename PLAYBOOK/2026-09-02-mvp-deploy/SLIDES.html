L'enjeu · 03

Un prototype dans un artifact Claude, c'est une app en cage.

Narration L'artifact avait sa propre API de stockage (window.storage) et appelait Anthropic directement avec la clé dedans. En dehors de Claude.ai, il ne fonctionne pas. Et même à l'intérieur : zéro persistance, zéro sécurité, impossible à partager.
Terme à retenir
Cloudflare Pages Functions
Serveur V8 isolé qui tourne à l'edge — fetch natif, pas de Node.js. On y stocke les clés API. Le client n'y a jamais accès.
La décision stack était la première bifurcation. Scène 4.
Le choix stack · 04

Cloudflare plutôt que Netlify. Supabase plutôt qu'un fichier JSON.

NarrationUn choix qui détermine tout : gratuit sans limite de déploiements, clés API côté serveur, persistance cross-session. Et zéro config serveur.
Cloudflare Pages

Hébergement + edge fonctions

  • Déploiements GitHub illimités (Netlify = 300/mois gratuit)
  • Pages Functions en V8 isolate — fetch natif, pas de npm
  • ANTHROPIC_API_KEY et SUPABASE_SERVICE_ROLE_KEY côté serveur uniquement
Supabase

PostgreSQL + REST API

  • Une table : device_id (clé) + data (JSONB blob complet)
  • Upsert avec Prefer: resolution=merge-duplicates
  • Pas de client lib — fetch natif sur PostgREST
  • device_id = UUID en localStorage, jamais d'auth
Stack décidée. 4 fichiers à écrire. La méthode ensuite.
La méthode · 05

MAESTRO : un gate de cadrage, puis zéro interruption.

Narration Pour la phase UX Push, on a invoqué /maestro. Un seul moment de décision : le gate CADRAGE.md avec 4 choix fermés. Après validation, la machine tourne seule jusqu'à la livraison.
A1

Focus strict

Masquer complètement la suite. Seule la prochaine action est visible. Lien "Voir la suite (N)".

B1

Panneau inline

Recherche IA déployable sous la tâche. Pas de modal, pas de drawer. Contexte préservé.

C1

Ordre implicite

Pas de badge P1/P2/P3. L'ordre des tâches est la priorité. Bouton "Reclasser" pour reprendre la main.

D1

Vues détail only

On ne touche pas le treemap d'accueil. Scope maîtrisé, risque de régression nul.

Les experts ont débattu. Les décisions sont prises. On produit. Scène 6.

Narration Le prototype vivre.html avait 3 points de contact à couper et remplacer : le stockage artifact, le fetch Anthropic direct, et le titre. Tout le reste — treemap, logique, CSS — est resté intact.

Livrable 2 — Focus strict · 07

L'utilisateur voit une tâche. Une seule.

Narration Pour les projets à une catégorie : la "PROCHAINE ACTION" occupe tout l'écran. Les tâches suivantes existent — on voit juste "Voir la suite (2 tâches)". Un chiffre qui rassure sans distraire. Inspiré de Goblin.tools Taskmaster.
Terme à retenir
Progressive disclosure
N'afficher que ce qui est pertinent maintenant. Le reste existe mais attend. Réduit la charge cognitive sans cacher d'information.
Une tâche visible, l'IA peut l'enrichir en contexte. Scène 8.
Livrable 3 — Recherche IA inline · 08

Un clic sur la loupe. 6 options contextuelles. Zéro prompt à écrire.

Narration L'IA reçoit le titre du projet, le résumé, et le titre de la tâche. Elle retourne 4 à 6 options condensées. L'utilisateur coche ce qui l'intéresse. Le panneau reste ouvert même après que la tâche est marquée faite. Même sur les tâches saisies manuellement.
Modèle de données

item.research

{ options: [{text, checked}], open: bool, loading: bool, fetchedAt }

Stocké dans le JSONB Supabase comme le reste de l'état. Pas de table séparée.

UX

Inline, pas de modal

Le panneau s'ouvre sous la ligne de tâche, pousse le reste vers le bas. Fermable. Persistant à travers les recharges. Checkbox onChange → debounce persist → Supabase.

L'IA trie aussi les tâches par priorité. Scène 9.
Livrable 4 — Reclasser par priorité · 09

Un clic. L'IA décide qui passe en premier.

Narration Le bouton "Reclasser par priorité" envoie toutes les tâches non terminées à l'IA, qui retourne les IDs dans l'ordre recommandé. Les tâches se réorganisent. La "PROCHAINE ACTION" change. Aucun badge visible — l'ordre dit tout.
Terme à retenir
Implicit priority
La position dans la liste est la priorité. Pas de badge P1/P2/P3 qui charge visuellement chaque ligne — l'ordre porte l'information.
Tout a failli rater à la mise en prod. La vrai histoire, scène 10.
Le grain de sable · 10

Le déploiement était en prod. L'app servait l'ancienne version.

Narration Après le commit e710c82 poussé sur GitHub, la page live ne contenait aucune des 3 nouvelles features. Git confirmait que le remote était à jour. Cloudflare n'avait pas redéclenché son build.
1
Diagnostic
document.documentElement.innerHTML.length → 49 444 octets. Fichier local → 57 101 octets. Cloudflare servait le build 5282cb3, pas e710c82.
2
Cause
Webhook GitHub → Cloudflare silencieusement raté. Git push OK, build non déclenché. Aucune alerte côté Cloudflare.
3
Fix
git commit --allow-empty -m "chore: trigger redeploy" + push. Cloudflare rebuild déclenché. Confirmé via poll : until curl -s URL | grep -q "research-icon-btn"; do sleep 10; done.

Le truc que personne te dit · 14

Un webhook raté ne prévient pas. Et c'est le test qui détecte, pas git.

Narration Le piège Cloudflare : git push dit "Everything up-to-date" et GitHub montre le bon commit — mais Cloudflare n'a rien construit. Le seul signal fiable : comparer la taille du HTML servi au fichier local. 49 444 ≠ 57 101. Le reste est silence.

Le réflexe à adopter : après tout déploiement, vérifier que la page live contient une string qui n'existe que dans la nouvelle version. Un curl -s URL | grep -q "nom-de-classe-unique" vaut mieux qu'un regard sur le dashboard.
